## 纠正此前页面方案

此前“第一次使用 / 已有空间”的选择只能提示用户，无法判断一个无痕浏览器里的学校账号是否已有空间。用户指出再次点击创建会产生新身份，这个问题成立。本版不再依赖自称首次或 UI 提示防重复，直接阻断未知身份匿名创建。

## 当前行为

- 旧 `/tools/device-login` 入口验证返回路径后进入唯一 `/tools/login` 页面。
- 第 1 步核验本人身份：设备码自动生成，但不建立账号/空间。将本人绑定句发给原已授权 Agent；不能以学校登录、昵称、学号或公开 DEV 码猜 owner。
- 第 2 步明确核验并接入原空间：服务端按真实 Agent grant 和来源会话查 owner，多浏览器复用同一工作区。保留浏览器原有私密身份的旧访客也可主动恢复原空间。
- 第 3 步只有授权身份、工作区和绑定一致才显示进入按钮。请求失败、身份变化、签名上下文无效时拒绝进入，不覆盖、合并或删除记录。
- 没有直接创建按钮。原 `POST /api/v1/auth/visitor/session` 现在是已知身份恢复接口：有效会话直接保留；已登记私密 Cookie 恢复旧身份；未知 Cookie 或无 Cookie 401，不增加任何 owner/workspace；待绑定到其他可信身份的设备 409，必须走原授权 claim。
- 原注册账号登录依靠可信服务端登录主体和既有 owner 唯一约束，可复用自己的空间；不扩大注册名单。

## 不能宣称的能力

接口仍没有可验证的校园账号 ID。完全首次用户没有可信工具站身份时，本轮选择安全地拒绝匿名新建，并提示完成支持的本人身份登录；**这不是已经实现全校用户免注册首次入驻**。要做到校园账号全局唯一首次建立，需要受支持的可信身份来源，不能通过学校登录截图、聊天文本或浏览器指纹替代。

旧版已经分别建立的多个访客身份不自动合并或清除。公用浏览器配置会共用私密 Cookie，不代表自动识别当前学校用户。

## 数据库守卫与部署

新增 `deploy/cloudbase-identity-pilot/visitor-identity-first-migration.sql`，在已执行 `browser-visitor-migration.sql` 的环境追加一次；不重跑旧 schema/迁移，不删除或迁移任何数据。

迁移包装 RPC：同一事务/同一旧全局锁下先确认 challenge 对应已登记且仍获批准的 owner，未知者拒绝，再调用旧恢复逻辑。旧匿名建立函数从 PUBLIC/anon/authenticated/service_role 撤销执行权，不能通过旧函数名绕过。`visitor_probe` 必须返回 `browser-visitor-identity-first-v2`，缺守卫的新应用拒绝启动。

打包脚本必须带新迁移；不把生产迁移混入构建自动执行。旧版应用可能因 probe 版本变化无法启动，回退不得撤掉新守卫或重开匿名创建，需支持新版保护的应用版本。

本分支已整合 origin/main `0051687`（PR #15/#16/#17），保留 B 的 JSON 上传反馈和原生文件选择框修复，并联合回归。Agent 追加规则只改仓库源码，未改在线已发布配置或权限。
