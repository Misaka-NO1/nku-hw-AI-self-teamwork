# 第6模块：培养方案与学分实施规划

日期：2026-10-08。状态：规划完成，未开展本轮功能修改或线上部署。

## 最新实施安排（以本段为准）

用户明确：现在先完成规划，后续将上线接口供AI读取网页信息。本阶段不实施截图/成绩单上传，不接入或猜测教务接口，不修改线上应用。前文导出/截图路线保留为可选方案，不作为当前主路径；开发工期估算待实际接口能力确认后重新评估。

主路径：本人通过未来提供的接口授权读取 → 接口返回页面信息及来源范围 → 校验学生方案、模块层级和修读状态 → 确定性规则处理 → AI解释模块缺口与修读方向。

### 接口对接清单（待接口上线确认，不代表现有能力）

接口至少需要提供或让接入层提取以下内容：

- 方案：专业、入学年级、方案版本；确实未展示的字段保持未知。
- 来源：页面类型、采集时间、来源地址或可追溯标识，是否预审，是否读取全部页面/分页。
- 模块：稳定标识、名称、父模块、最低学分、所有子项满足/至少一项满足等条件，以及页面显示的缺口。
- 课程：课程代码、名称、所属模块、课程学分、必选修要求、成绩/通过状态、在读状态及备注。
- 计入口径：页面显示的实修/要求学分、是否包含在读和预审记录；未知则不得自动解释为已获得。
- 本人访问边界：接口按授权身份决定资源归属，不由模型传入学号切换学生。读取权限、失效与失败由接口明确返回。

字段名称和数据形式待实际契约确定，可接结构化数据或页面正文；不要提前冻结一个不兼容的接口。若只有网页正文，先提取结构化候选并核对关键字段，不能用模糊提取直接输出确定进度。原则上不需要把姓名、学号带进解释报告。

### 分析流程

1. 校验来源与覆盖：未授权、读取失败、缺页或版本不明明确说明，不用演示补个人结果。
2. 重建模块树和组合条件：所有子项、至少一项、必修集合分别判断；父子学分不重复累加。
3. 分开口径：已通过、在读、未通过、待认定分别记录；教务预审显示与已通过记录核算分别展示。
4. 生成模块缺口：学分缺口与缺必修独立检查；未知替代/互斥/认定规则保留待确认。
5. 生成建议：先列必须补的课程/子模块，再列可选模块方向；在读仅给通过后的条件性说明。
6. 可选课程推荐：只有实际取得开课学期、先修与选课条件后才建议具体课程或学期；否则停在模块建议。

### 用户看到的结果

首先说明本次数据来源、采集时间及分析范围，然后用模块表显示：模块名称、要求、已通过、在读、仍需补修、下一步。表后给简短优先建议与理由，最后列待核实项。不给无依据的整体完成百分比，不把预审结论称为最终毕业审核。

### 接口上线后的验收

- 方案专业/年级/版本正确匹配；同名不同课程代码不误合并。
- 全部子项与至少一项满足条件正确；父子模块学分不重复累计。
- 在读不冒充已取得；学分足够但缺必修仍显示未满足。
- 重复修读、课程替代及未知认定不擅自计入。
- 截断/分页缺失只分析覆盖范围；无权限和失败不显示旧结果或演示结果。
- 教务显示缺口与独立核算不一致时并列解释、标明待核实，不静默覆盖。
- 学校主Agent实际读取当次接口结果，正确给模块建议；固定演示仍保持独立入口。

### 本次与后续交付边界

本次已交付规划和接口信息清单，不新增功能或部署。接口上线后先检查真实返回样例、权限与覆盖，再完成数据适配、必要规则扩展、结果展示、平台接入和上述验收。真实复杂规则仍以正式方案原文或可核实教务规则为依据，接口能读到页面不等于全部规则已具备。

## 用户确认的最终目标（2026-10-08追加）

根据学生本人的培养方案与已修学分，说明还应修哪些模块、各模块缺多少学分、缺哪些必修，并给出有依据的修读优先建议。用户提供教务“计划完成情况”截图作为目标参考；截图仅覆盖部分页面，不据此认定完整个人进度，也不复制姓名、学号等身份字段到规划。

目标输出包括：模块名称、要求学分、已通过计入学分、在读/预审计入学分、仍需补修的学分或课程、规则依据和待确认项。优先顺序先解释缺必修和必须满足的子模块，再讨论可选模块；具体下学期能否修某门课还依赖开课、先修和选课条件，信息未取得时仅给模块方向。

截图表明真实方案存在父子模块、“所有子项均应满足”和“至少一项满足”等组合条件。现有平面模块加最低学分的内核不足以完整表达这些条件，应新增明确的规则结构并逐项验证；父模块与子模块的汇总不能重复累加。

截图部分课程同时显示计入学分/通过标记和“在读”。教务预审口径与已取得学分口径必须分开保留，未核实前不能直接将截图“实修学分”当作全部已经通过。报告分别回答“按当前教务预审显示还缺什么”和“按已通过记录还缺什么”，并说明在读通过后可能覆盖哪些缺口；在读不能承诺一定取得学分。

输入路线补充：优先支持用户主动提供完整的培养方案/计划完成情况导出文件，或连续完整截图及成绩记录。教务完成情况是已有缺口和模块结构的重要来源，可先做来源明确的解释，再做独立核算；不必先接通教务自动抓取。解析后的模块层级、课程代码、学分、状态、备注及页面覆盖范围须供本人核对。单张截断图片只能给可见范围的分析，不能给全方案结论。

分期调整：第二阶段增加“个人计划完成情况解析与核对”的产品设计；第三阶段以“模块缺口＋修读方向建议”为验收目标。第一版可直接解释已核对的教务缺口，独立核算只覆盖已支持且核验的规则，不将两类结果混为一谈。

## 原计划与当前基线

依据：C模块任务书、C-02正式培养方案阻塞记录、2026-10-06给D的剩余模块交接、C-progress及2026-10-08收尾执行记录。

原计划以NK-GeniOS为对话入口，辅助网页用于展示；C负责培养方案资料、规则内核和展示，D负责引用解析、接口、平台绑定与实际验收。首个正式样本限定一个专业、一个入学年级、一个方案版本。复杂未支持规则保留needs_policy，不给官方毕业资格结论。

当前已有：固定演示方案、成绩、学分内核、REST/MCP适配、网页模块表和学校第6项入口。历史线上固定演示正反例有验收记录；本轮只观察了编排页模块指引，没有重新运行线上审计。本轮现有学分测试12项通过。

当前缺少：本地正式培养方案及逐条规则核验表，真实成绩解析通路；网页请求仍固定为演示引用。交接书曾提及knowledge/degree/cs-2025/plan-rules.md，但本地未发现；不视为已交付，也不据路径推定首个专业或年级。

## 第一阶段：核对资料交付与固定演示收尾

1. 核对C交付的相关分支/PR和附件，确认正式方案是否已存在；找到后核对专业、入学年级、版本、发布单位、适用范围。找不到则更新C-02，明确需要的原文件。
2. 整理现有支持规则、未支持规则和来源字段。排查未核验方案仍产生学分数字的问题；方案未核验时不展示确定进度。补成绩与方案版本匹配的校验及测试。
3. 学校新对话验收：选择6只给指引；明确演示才调用；未知方案保持原值拒绝；工具失败不搬历史结果；跨模块切换正确。

交付：演示能力清单、错误边界、当次工具实证。正式资料缺失不阻止这一阶段完成。

## 第二阶段：一个正式方案的可追溯查询

1. 建立唯一方案数据源：专业、入学年级、版本、正式课程代码、课程名称、学分、必选修属性、模块归属；建议学期仅在原文有依据时收录。
2. 建立规则核验表：每条必修要求、模块最低学分、重复修读和归属规则对应原文页码/条目；未知规则空缺，不能为了运行填默认值。
3. 增加方案查询入口及按方案精确筛选，支持问必修、模块要求、课程归属，答案附来源。知识库用于解释原文，确定学分计算继续由后端完成。
4. 边界验收：不同专业/入学年级/版本不混用；同名不同代码不合并；未支持的互斥、嵌套模块、体育类别、通识组合条件和学分认定明确列出。

交付：一份正式方案原件、结构化课程与规则、核验表、查询正反例。规则核验不完整时可查原文，但不能给完整学分完成结论。

## 第三阶段：正式方案与成绩的进度试点

前置条件：所选方案的必要规则已核验，成绩输入方式和本人归属明确。

第一版先用负责人确认的测试成绩样本验证正式方案计算，样本明确标注虚构/脱敏性质。真实成绩试点需要另行接入本人授权、记录来源、数据覆盖与版本匹配，不能直接放宽原只接受固定引用的接口。

用户流程：选择专业/年级/方案版本 → 选择有权访问的成绩记录 → 核对来源与覆盖 → 后端核算 → 展示各模块已计/要求/缺口、缺必修、未归属课程、未决规则。

结果优先显示课程和模块名称；内部ID作为诊断信息。区分已通过、在修、未通过与待认定；解释记录为何排除，不将规则不足显示成确定缺课或已完成。

交付：匹配校验、可解释进度结果、接口及学校端到端验收。仅完成已支持规则下的进度参考，不代替学校毕业审核。

## 工作分工与实施顺序

- C：找齐原件、核验表、方案课程目录；修规则内核和结果展示。
- D：按更新后的契约解析方案/成绩引用，接入平台工具，处理错误和新对话验收。
- 负责人：确认首个样本的适用专业/年级、资料版本和试点范围，验收用户流程。
- B：后续需要课程代码匹配时协作，不重写课表/时间模块。

依赖顺序：交付核查 → 演示边界收尾 → 正式方案查询 → 规则核验 → 测试成绩核算 → 本人成绩试点。资料未到时，继续完成演示验收、规则模板及内核修复，不编造正式方案。

估算：交付核查及演示收尾1个工作日；收到资料后，单方案整理/查询/核验约2–3个工作日；进度试点约2–3个工作日。以上是初步工作量估算，不含资料等待、复杂政策确认和平台发布等待。

本规划不替代现有全项目收尾清单；云部署、日历多区间及OAuth等既有任务仍按收尾执行记录推进。后台推送此前不在需求范围。
