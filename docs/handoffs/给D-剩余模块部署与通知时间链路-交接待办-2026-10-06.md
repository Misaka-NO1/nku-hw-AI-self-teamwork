## 7. D 同时负责：通知/DDL → 课表 → 候选 → 后端写入

目标链路：

```text
用户发通知/日程/含 DDL 的文字或文件
  → 读取原文并记录来源、覆盖范围
  → 拆分事项，区分固定活动与截止任务
  → 提取时间、耗时、材料，缺项追问
  → 获取本人已确认课表及未完成的已排安排
  → 调用 B 算法，返回候选时间和简短推荐理由
  → 用户选择并明确确认
  → 写入所选工作区间，持久读回
  → 负责人日历前端展示；后续时间查询避开该区间
```

### 工作流要求

- [ ] 先把新文字通知做通，再扩展截图/PDF。采用来源定位、逐字段提取、证据回查、多事项拆分；不是仅给摘要。
- [ ] 旧 `WF_NoticeDraft_v1_Test / WF_D07_NoticeTime_Test` 保留回归，新通知不能只按固定 `fixture_id` 走预设答案。
- [ ] “明天/周五”参照不明、只有截止日期没有时刻、没有耗时等先追问；不默认 23:59、不猜耗时。
- [ ] `event_conflict` 返回活动冲突；`deadline_feasibility` 返回 `candidate_slots`。候选由后端计算，每项一行，首屏可给 3 项并支持展开。
- [ ] 候选窗口大于耗时时，由代码生成窗口内具体工作区间；用户改变耗时/偏好后重算，不能沿用旧候选。
- [ ] 保存的是“用户选定并确认的实际安排”，不是把所有候选都保存，也不是把 DDL 改成活动时间。
- [ ] 旧 NoticeDraft 的原文证据与 due 保留；新增日历字段通过明确扩展或旁表存储，按契约流程与前端约定。
- [ ] 普通参赛标准即可，不新增复杂体系；保留本人数据隔离、确认、幂等和凭证不进前端这几项基础保护。
