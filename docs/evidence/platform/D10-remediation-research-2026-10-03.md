# D10：503 与学校 OAuth 兼容的解决路径

## 本轮结论

重新加载腾讯云身份服务 `/healthz` 后，仍显示 `503 Service Temporarily Unavailable / nginx/1.17.8`。这不是学校会话过期页面。007 控制台仍显示正常、100%流量、1实例，已有日志确认启动完成和 `0.0.0.0:8080`；不能用这些控制台状态替代公网请求验收。

503 的确切来源未确定，**倾向入口/上游转发而非 OAuth 参数校验**，但还需要响应头和请求到达证据。不能因页面标有 nginx 就断言腾讯云平台故障。

## 代码与本地对照

- Dockerfile 暴露8080，Uvicorn监听0.0.0.0:8080，控制台端口也是8080；暂不支持“端口写错”的判断。
- 使用生产应用工厂、虚构配置、内存数据库替身、不发外网请求：OAuth关闭时 `/healthz` 为200 JSON（oauth_enabled=false），独立探针为200文本。此为本地对照，不证明云数据库/容器健康。
- OAuth开启时，把实际学校请求的参数形状（无PKCE、虚构10字符state）送入同一工厂：返回400 JSON invalid_request；补S256但保留短state仍400。没有产生授权事务、发放令牌或使用实际密钥。
- 现有缺PKCE/重复参数/限频测试与bootstrap关闭门禁测试：2项通过。没有重跑全套，也没有修改认证代码、SQL、云配置或学校插件。
- 官方Webshell仅显示Exit，重新选择/bin/sh也未出现可用提示符；未输入诊断命令，不能将这当作容器内部端口检查结果。

## 503 下一步：先取得可判别的证据

1. 从同一健康请求取得 `X-Cloudbase-Upstream-Status-Code` 等响应头，区分应用与网关响应。浏览器当前控制接口不提供网络响应头；未用其他通道绕过先前客户端阻止。
2. 若当前入口可正常访问但仍503，给同一服务增加**仅健康请求**的非敏感到达日志：固定路由名、build_id、状态，不记请求头、Cookie、查询字符串、账号或凭据。本轮没有实施或部署此变更。
3. 若健康请求到达应用，排查数据库探针超时/服务异常；若未到达，核查当前实例就绪与公网入口转发，携带版本007、启动时间、请求时间及脱敏错误提交腾讯云工单。工单未提交。
4. 不盲目删除服务、反复上传同一包、加内存或购买域名。自定义备案域名是正式部署方向，不是已经证实的503修复；需要独立确认资源与费用。

官方依据：[HTTP访问排查](https://docs.cloudbase.net/run/faq/gw)说明可通过上述响应头判断错误来源；[部署失败排查](https://docs.cloudbase.net/run/faq/deploy)列出监听端口、进程稳定性等检查；[公网访问](https://docs.cloudbase.net/run/deploy/networking/public)说明服务默认域名与版本无关。这里不把官方可能原因当成本次确诊。

## OAuth：有路径，但不能把兼容等同安全验收

项目现有Python与PG RPC都要求S256，以及16–256字符state。16字符是本项目门槛，不是OAuth通用的固定最短长度；观察到10字符也不能单凭长度推断随机性、熵或回调验证行为。学校当前可见配置没有PKCE入口，实际请求未携带challenge，尚未验证客户端的state校验或令牌保密存储。

| 路径 | 可行条件与限制 |
| --- | --- |
| 保留现有S256方案 | 学校客户端实际生成challenge并在兑换时发送同事务verifier；仅工作区管理员权限不足以自行修改学校服务器实现。 |
| 独立的传统保密客户端兼容试点 | 技术上可另行设计，但属于既定保护的降级，不是改一行代码的安全修复。必须先验证学校服务端保密存储、state与浏览器事务绑定、拒绝伪造/重放回调；再获明确风险例外。仅两个虚构账号、demo:read、短令牌、严格客户端/精确回调/一次性码/显式同意/登出撤销；现有严格客户端仍不变。条件未证明时不启用。 |
| 暂保留公开Agent + 独立登录工具页 | 不降低身份保护，可继续公开资料与本人浏览器操作；但个人记录尚不能由学校Agent直接读取，不能称全部功能成品。 |

依据 [RFC 9700 §2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1)：public client必须使用PKCE，confidential client推荐使用PKCE；它还要求防止授权码注入。由此不能把“没有PKCE”说成所有OAuth绝对无法运行，也不能把client_secret+state直接宣称等价安全。传统兼容方案需要独立威胁分析及例外，不自动满足现项目契约。

固定challenge、把verifier填入Header、授权服务器自行补PKCE或增加一个转发代理，都不能证明学校原始事务被PKCE保护。SYS_USERID文本与共享服务令牌也不能代替可信逐用户身份。

## 推荐顺序

先用响应头/非敏感健康到达日志定位并恢复503；之后优先验证学校S256支持。若确实不能支持，负责人可以另行批准传统保密客户端的虚构数据兼容试点；批准之前仍保持OAuth关闭，不修改旧服务/表或公开主Agent。本轮只是探究与对照验证，没有上线任何兼容降级。
