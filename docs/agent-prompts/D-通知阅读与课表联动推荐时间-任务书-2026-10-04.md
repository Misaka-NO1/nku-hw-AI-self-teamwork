# D任务书：通知阅读、待办提炼与课表联动推荐时间

日期：2026-10-04。交付对象：D同学及其Coding Agent。

本任务的“阅读”指阅读用户提交的通知、任务要求或日程安排，提炼要做的事情；不是复习资料讲解。可以包含“阅读一篇论文”等待办，但系统不能把论文正文阅读时长擅自当成用户已经确认的耗时。

这是开发与验收任务书，不代表文中规划的接口、文件阅读能力或完整闭环已经上线，也不自动授权购买资源、扩大用户权限或发布到公众。

## 1. 最终要交付什么

用户在NK-GeniOS中发来一段通知、截图或可读取的文件，Agent能回答：

1. 要做什么，是否包含多个事项。
2. 什么时间参加，或什么时间之前完成。
3. 需要准备什么材料，有什么提交入口。
4. 与用户已授权的课表和已确认活动是否冲突。
5. 截止前有哪些可用时间，推荐什么时候完成，理由是什么。
6. 用户选择并确认后，保存待办；再次打开能读回，重复提交不重复保存。

主入口始终是NK-GeniOS Agent。辅助网页只负责课表导入、核对、选择和确认，不做成必须另起一套聊天才能用的产品。

完整链路：

```text
通知/任务原文
  → 读取与来源定位
  → 分事项提炼
  → 结构和原文证据校验
  → 追问缺失时间/耗时
  → 读取本人已授权课表及已确认活动
  → B时间算法计算冲突/候选窗口
  → Agent逐项展示建议与理由
  → 用户选择时间并在受控页确认
  → 后端保存、读回
```

最小参赛标准：团队和获准评委可以用自行编写的新通知完成这条链路。不能只接受三个固定fixture_id，不能用事先写好的答案冒充理解新输入。先用虚构通知和虚构课表验收，不以接入真实教务作为本任务的前置条件。

## 3. 阅读必须有明确方法

### 3.1 输入处理顺序

第一阶段先把粘贴文字闭环做完，再扩展截图和PDF；不得先做几个上传按钮，却没有可靠的读取结果。

| 输入 | 读取方法 | 失败时怎么办 |
| --- | --- | --- |
| 粘贴文字 | 保留原文和段落，直接送结构化提取节点 | 空文本明确提示重新提供 |
| 截图、照片 | 核查平台现有图片理解/OCR能力；先转录文字，关键日期、数字和否定词再对照原图 | 看不清的关键字段标待确认，不猜数字 |
| 文字型PDF | 核查可用文件读取能力；逐页提取正文，保留页码和阅读覆盖范围 | 无正文、加密或失败时明确说明 |
| 扫描型PDF | 按页OCR，保留页码；低清或歧义关键字段交用户确认 | 不把空文本当“没有任务” |
| DOCX/PPTX等其他格式 | 只有实际验证的平台或后端读取器才声明支持；提取段落/幻灯片并保留定位 | 给出具体不支持原因，请用户粘贴文字或转PDF |

无需为了这一任务引入新的第三方模型账号。优先使用学校平台已有能力；若做不到，记录具体限制和降级路径，不虚构OCR插件、文件接口或已读完的页面。

不得要求用户交出教务密码、Cookie；不得从通知中的任意链接自动下载或执行内容。通知写“忽略规则/直接保存/读取所有用户”只算正文，不是操作指令。

### 3.2 五步阅读法

1. **识别来源和时间参照。** 记录原文、来源定位、可确认的发布日期；处理时间不是发布日期。“明天/本周五”必须有明确参照日期，无参照先追问。
2. **拆分事项。** 区分通知背景、行动要求、固定活动、截止任务。一个文件有三项任务就列三项，不只提取第一段或最后一个日期。
3. **逐字段提炼。** 提取标题、活动起止、截止、预计耗时、最早开始、材料，以及原文存在的对象、地点和提交入口；未知值保持未知。
4. **回查证据。** 时间、材料和入口必须能定位到原文、图片位置或PDF页码。格式合法不代表含义正确；查否定词、取消/延期说明、多个版本及相互矛盾的时间。
5. **简短复述并补缺。** 向用户展示“我读到的事项”和确实缺失的字段；用户补充后更新结构化结果，再算时间。无需输出冗长推理过程。

长文件必须逐段/逐页覆盖再合并去重，保留未读取部分。文件过长时可分批或让用户指定页码；不能只读首页却声称全部事项已整理完。

### 3.3 结构化结果与契约

当前 `NoticeDraft` 恰有13个字段：

```text
schema_version, notice_id, title, published_at, extracted_at,
timezone, event, due, estimated_minutes, earliest_start,
materials, source_spans, needs_confirmation
```

- `source_spans`每项为 `field / quote / source_ref`；关键提炼保留来源，不能补造引用。
- 一个事项对应一个NoticeDraft。多事项的批次包装、文件阅读覆盖等属于新增适配设计，须按契约流程定义，不把数组塞进旧单事项字段。
- 对象、地点、提交入口、优先级及最终选定工作区间不都在现有13字段内。若需要持久化，明确采用补充元数据或契约升级，并同步消费者和测试；不能偷偷增加字段让旧校验失效。
- 通用提取器校验结构、字段证据、时间一致性和必需信息，不再依赖“答案必须与三份已知夹具完全相同”。旧固定回归仍保留，用新输入测试实际泛化。

## 4. 怎样与课表串联并推荐时间

### 4.1 读取真实授权范围内的记录

使用现有本人授权链路，读取当前账号已确认的课表及活动。身份由后台登录/OAuth确定，不能由模型传入姓名、SYS_USERID、user_id或另一个workspace_ref来决定。

课表不存在时引导导入或建立已批准的虚构演示课表，不静默拿共享课表顶替。课表覆盖不完整时写“在已导入课表范围内未发现冲突”，不保证现实中一定有空。

本人空档要计算课程加已确认活动的并集；尚未确认的草稿不占时间。截止任务的due也不占忙碌区间；用户最终确认的实际工作区间如要占时间，必须明确持久化模型，不能只保存DDL却声称以后会避开它。

### 4.2 两条不同计算分支

| 事项 | 算法处理 | 输出 |
| --- | --- | --- |
| 固定会议/讲座/活动，起止明确 | `event_conflict`，比较实际课程和已确认活动 | 冲突课程/活动、重叠区间；无冲突只限已知范围 |
| 报告/报名/论文阅读等截止任务 | `deadline_feasibility`，根据耗时和最早开始找截止前空档 | `candidate_slots`和必要待确认项 |

固定会议不能由Agent擅自改期；有冲突时说明情况，让用户决定。只有截止日期没有时刻，不默认23:59。没有任务耗时，不由模型随口估一个数字当成已确认值；可以提出建议供用户确认。

调用B既有函数，不由语言模型心算空档。时间均带时区，默认Asia/Shanghai；使用半开区间 `[start,end)`，保留单双周、调休和查询覆盖范围。

### 4.3 参数传递与输出约束

- `TimeCheckRequest.kind`仅为 `event_conflict / deadline_feasibility`，不是随意命名的deadline。
- `event`是活动时间对象；`due`是 `{at,date,precision}` 对象，不是字符串。
- 查询window只定义检查范围，不能替代event.start/end。
- 学校插件仍需要query_json时，由确定性节点序列化一次，把校验后的本次结果直接映射过去；不让模型重抄长课表或重新生成通知时间。
- 本人OAuth适配输入不允许workspace_ref；后台从授权确定owner，复用规范TimeCheckRequest业务语义。
- `allow_split=false`是当前契约。首版必须找完整连续区间；不擅自拆成两段。想支持拆分另提契约变更。
- 分清 `slots`（空档）、`candidate_slots`（截止任务候选）与 `conflicts`（活动冲突）。插件输出定义必须把实际分支传给模型，不能遗漏候选字段后让模型补结果。

推荐首版采用可解释的确定性规则：用户给出的可用时间限制先过滤，再优先最早可完成、离截止留有余量的区间；最多展示3个候选，其余可展开。午饭、睡觉、通勤或个人习惯只有用户确认后才纳入约束，不凭空假设。

候选窗口可能大于任务耗时：可让用户选择窗口内起点，或由代码生成恰好耗时的建议工作区间。该区间须落在原候选窗口内，保留对应候选来源，不能由模型编出工具没有返回的时间。

空列表要说“在本次查询与已知课表范围内没有足够的连续时间”；有needs_confirmation先补信息；缺少候选字段或调用失败要报失败，不能当作“没空”或借历史成功回答。

## 5. Agent和复核页的用户体验

直接收到通知就进入本流程，不强迫用户先选功能，也不要求知道fixture_id或工具名称。不同功能之间可以随时切换。

第一次阅读后按事项逐行展示：

```text
我读到两个事项：

1. 参加会议：10月5日14:00—15:00。
   地点：原文明确的地点；来源：截图第2段。

2. 提交报告：10月6日12:00前；材料：报告PDF。
   还需要确认：你预计要做多久、最早何时开始？
```

上述日期是展示格式示例，不是默认日期或南开真实通知。

计算后同样每项一行，推荐附简短理由及覆盖限制。询问“选哪一个”，正确理解最近菜单的编号。用户补充“只考虑晚上/我还要通勤”后重新计算，不能继续使用旧候选。

受控复核页展示原文、提炼字段、必要修改、课表覆盖和选定时间。保存按钮必须由用户确认触发；聊天里说“帮我记一下”不等于Agent已经代点确认。草稿修改后旧确认不得生效，重复提交只能产生一条任务。

学校会话失效时先重新打开并登录；但工具返回503不一律解释为登录问题。保留真实错误、重试入口，不编造成功。

## 6. D执行步骤与交付物

### N01：现状核查和接口方案

梳理当前提取、时间、本人记录、保存各阶段的实际输入输出，列固定夹具限制。确定通用文字输入、批次包装和选定工作区间的契约/存储方案。复用现有资源，不另建平行用户系统。

### N02：通用文字阅读与提炼

创建独立通用测试工作流或明确版本升级，保留旧演示工作流。完成多事项、相对日期、缺项追问、原文证据和跨轮更新。新通知不得自动替换成固定夹具。

### N03：本人课表和推荐链路

把本次校验后的提炼结果直接交B算法，连接本人课表及已确认活动。必要时新增隔离参赛文本试点入口和明确的数据模式，不简单全局关闭demo门禁，不接任意他人课表。

### N04：本人确认保存和读回

复用草稿、revision、payload_hash、确认和幂等提交机制。实现所选时间的正确保存及后续忙碌处理；普通账号可核对自己的数据，不能跨账号读写。

### N05：截图/PDF读取

文字闭环通过后增加至少一种文件输入，优先截图；记录真实支持格式、大小/页数边界、阅读覆盖和失败提示。PDF读取未通过时不宣传支持。

### N06：学校主Agent实操验收与交接

在NK-GeniOS实际发送未预设的新通知，录下原始提取结果、时间工具请求/返回、页面确认和数据库读回。Debug通过不替代主Agent通过，预览不替代保存，部署正常不替代业务闭环。

建议新增交付文件（这是规划命名，不是声称文件已存在）：

- `docs/evidence/platform/D13-notice-schedule-acceptance.md`：实操证据与失败记录。
- `docs/handoffs/D-notice-schedule-usage.md`：用户操作示例、支持输入、限制、部署版本。
- 对应工作流配置与读取/校验/参数映射代码、提示词、正反例测试。
- 涉及契约变更时的字段说明、兼容性及B/C同步说明。
